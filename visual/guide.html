触发：webhook 如何做到「一推就跑」

你敲下 git push 之后，代码变更如何变成一个构建任务

前端已实现后端待实现▼

发生了什么：你在 GitHub 仓库设置里填了一个 URL 和一个密钥。从此每次 push， GitHub 主动向这个 URL 发一个 HTTP POST 请求，请求体是一个 JSON，写着：谁推的、推到哪个分支、 commit 的 SHA、提交信息。

GoPulse 收到后做四件事：验签 → 限长 → 解析入队 → 立刻回 202。真正的构建在后台异步进行。

小白类比

打个比方
把 webhook 想成外卖平台的接单提醒。

轮询（polling）= 你每隔一分钟打电话问餐厅「有我的单子吗」—— 99% 的电话都白打，而且平均要等半分钟才知道。
webhook = 餐厅一有新单子就主动打你电话—— 零延迟，零无效通话。

「hook（钩子）」的意思就是：你在别人的系统上挂了一个钩子，事情发生时它来拉你。

轮询 vs webhook

维度轮询（每分钟问一次）webhook（事件推送）
延迟平均 30 秒（取决于间隔）毫秒级
无效请求99% 得到「没变化」0
平台侧压力每仓库每分钟一次只在真有事时一次
实现复杂度简单需要公网可达地址 + 验签

为什么必须验签：你的 webhook URL 是公网可访问的。任何人都能往这个 URL POST 一个假 JSON， 声称「某仓库刚 push 了」，然后你的系统就会去构建一个不存在的 commit，或者被恶意触发去部署。

防御手段是 HMAC-SHA256 签名：

HMAC 验签原理

GitHub 侧： 用【共享密钥】对【请求体原文】算一个哈希 ──▶ 放进请求头 X-Hub-Signature-256: sha256=5d41402abc... GoPulse 侧： 用【同一个密钥】对【收到的请求体】算哈希 ──▶ 和请求头比对 │ ┌─────────────────────────────┴──────────────┐ ▼ ▼ 一致 → 确实是 GitHub 发的，且内容未被篡改 不一致 → 401 直接拒绝

HMAC 的四个安全性质

哈希不可逆
拿到签名反推不出密钥
密钥不上网
网络上传输的只有哈希结果，密钥双方各自保存
改一字节全变
内容不可能被中途篡改而不被发现
每项目独立密钥
一个项目的密钥泄漏，不影响其他项目

最容易被新手写错的坑：同步构建

坑 / 必须守住
GitHub 的 webhook 有 10 秒超时，而一次构建要几分钟。如果你在 webhook 处理函数里同步执行构建：

流程

GitHub 等 10 秒 ──▶ 超时 ──▶ 认为你挂了 ──▶ 标记 webhook 失败 ──▶ 稍后重试 │ ┌───────────────────────────┘ ▼ 你又构建一次，又超时 ──▶ 无限重试风暴

所以必须「收到就入队，马上应答」。这正是 202 Accepted（而不是 200 OK） 的语义 —— 「我接受了你的请求，但还没处理完」。

幂等去重：为什么要做

为什么这样设计
网络会重试，GitHub 也会重试，同一个 push 可能收到两次 webhook。如果不去重，就会构建两遍、部署两遍。

做法：以 (commit_sha + ref) 作为唯一键，短时间内重复的直接丢弃。
这个性质叫幂等（idempotent）—— 同一操作执行一次和执行多次，结果相同。

小白类比

打个比方
餐厅的取号排队系统。

服务员（webhook 处理函数）不会站在门口给你现做一道菜 —— 他给你一张号码牌，记在本子上，然后立刻接待下一位。

内存队列 vs 数据库队列

内存 channel数据库表
实现make(chan *Job, 100)一张 builds 表 + state 字段
进程崩溃队列里的任务全丢重启后继续处理
可观测性看不见队列内容可以直接 SQL 查
多实例扩展做不到天然支持
性能极快略慢，但对 CI 场景完全够用

为什么内存队列是致命的：CI 服务器恰恰容易崩（OOM、被 kill、机器重启）。 用内存队列的话，用户 push 了代码，界面上什么都没发生，也不知道为什么 —— 这是最糟糕的体验。 所以设计上用数据库表当队列。

部分索引：只给活跃任务建索引

CREATE INDEX idx_builds_state ON builds(state)

并发编程最经典的坑：两个 worker 抢同一个任务

坑 / 必须守住
假设两个 worker 同时来取任务，如果「查询」和「更新」是两步：

流程

worker A: SELECT * FROM builds WHERE state='queued' LIMIT 1 ──▶ 拿到 #100 worker B: SELECT * FROM builds WHERE state='queued' LIMIT 1 ──▶ 也拿到 #100 │ ▼ 两个 worker 都去构建 #100 ──▶ 同一 commit 构建两遍，还可能互相踩

解法：把「查询」和「改状态」合并成一个原子操作

sql
-- SQLite：UPDATE ... RETURNING，数据库保证整条语句原子
UPDATE builds SET state = 'running', started_at = ?
WHERE id IN (
    SELECT id FROM builds WHERE state = 'queued'
    ORDER BY id LIMIT ?
)
RETURNING *;

-- PostgreSQL 的等价写法：
-- SELECT ... FROM builds WHERE state='queued' FOR UPDATE SKIP LOCKED

为什么这样

为什么这样设计
两个 worker 同时执行这条语句，数据库保证只有一方的 UPDATE 真正影响到那一行。 「谁改成功了，任务就是谁的。」—— 不需要应用层加锁，把并发控制交给数据库。

同项目串行化：一个更隐蔽的竞态

坑 / 必须守住
同一项目的两个构建如果并行部署，会出现旧版本覆盖新版本：

流程

web-api 项目的 #100（v1.0）和 #101（v1.1）同时部署： #100 部署 v1.0 ─────────────────────────▶ 完成（较慢） #101 部署 v1.1 ──────▶ 完成（较快） │ └──▶ 此刻线上是 v1.1 ✓ │ ▼ #100 后完成 ──▶ 线上变成 v1.0 ✗ 旧版本覆盖了新版本

解法：调度器按 project_id 分组 —— 同一项目一次只放行一个构建，不同项目之间可以并行。 这样既保证了正确性，又保留了并发能力。

并发调度：Go 的看家本领

goroutine、信号量限流、背压、context —— 四个概念讲透

后端待实现▼

这一节是整个项目技术含量最高的部分，也是选 Go 的理由。

小白类比

打个比方
goroutine = 轻量级的「工人」。

Java 线程像一个正式员工：招一个要几 MB 的「办公空间」（内存），公司养几千个就吃不消了。
goroutine 像临时工：只要几 KB，一个程序里开几十万个都没问题。

在 Go 里让一个函数后台并发执行，只需要在调用前加一个关键字： go doSomething() —— 就这么简单。

CI 系统的本质就是「同时管很多个正在跑的任务」，正好是 goroutine 的主场。

小白类比

打个比方
信号量（semaphore）= 停车场的车位。

不能无限并发：每个构建要起一个 Docker 容器，容器吃内存、吃 CPU、吃磁盘。 50 个人同时 push 就起 50 个容器，构建机当场 OOM 死机。

所以停车场只有 4 个车位（max_concurrency = 4）： 车来了有空位就进，没空位在门口排队；车走了腾出一位，放下一辆进来。

Go 里用带缓冲 channel 实现信号量 —— 简洁到令人发指

go
type Pool struct {
    sem  chan struct{}      // 容量 = 4，就是 4 个车位
    jobs <-chan *BuildJob
    wg   sync.WaitGroup
}

func (p *Pool) Run(ctx context.Context) {
    for job := range p.jobs {
        p.sem <- struct{}{}        // 占一个车位。满了就阻塞在这里等

        p.wg.Add(1)
        go func(j *BuildJob) {
            defer p.wg.Done()
            defer func() { <-p.sem }()   // 干完了，腾出车位
            p.execute(ctx, j)
        }(job)
    }
}

两个 Go 惯用技巧

为什么这样设计
① struct{}{} 是空结构体，占 0 字节内存 —— 纯粹用来计数，是 Go 里实现信号量的标准做法。

② go func(j *BuildJob){...}(job) 末尾那个 (job) 不能省 —— 必须把循环变量作为参数传进去。否则所有 goroutine 会共享同一个变量，最后全部执行最后一个任务。 这是 Go 并发最经典的 bug（Go 1.22 已修复循环变量语义，但显式传参仍是好习惯）。

背压（Backpressure）是个很重要的概念：当下游处理不过来时，把压力反向传导回上游，让上游慢下来。 在这个系统里，压力是这样一层层传导的：

背压链条：系统如何自我保护

车位满了（4 个都在跑） │ ▼ 新任务进不了 pool 堆在队列里 │ ▼ 队列也满了（queue_capacity = 200） Enqueue 返回错误 │ ▼ webhook 处理函数返回 503 Service Unavailable │ ▼ GitHub 收到 503，知道「对方忙」──▶ 稍后自动重试 │ └──▶ 【妙处】你什么都不用做，GitHub 自己帮你排队

踩过的坑

坑 / 必须守住
反面教材：队列满了还硬塞进内存（比如用无界 slice），最后 OOM 崩溃 —— 所有任务全丢。

原则：宁可拒绝，不可崩溃。 503 的语义就是「我现在忙，你等会儿再来」，各大平台都会正确处理它。

context：超时与取消的传递。Go 里所有可能「卡住」的操作都要传一个 context。 它像一根贯穿整个调用链的绳子，你一拉，链上所有环节同时知道「该停了」。

技术细节

go
ctx, cancel := context.WithTimeout(parentCtx, 30*time.Minute)
defer cancel()

// 这个 ctx 一路传给：Docker 创建容器、SSH 连接、HTTP 调 LLM……
// 30 分钟一到，或用户点了「中止运行」，所有环节同时收到取消信号

为什么必须有超时：网络会挂、Docker daemon 会卡死、SSH 会遇到永不响应的主机。 没有超时的阻塞调用 = 永久泄漏一个 goroutine = 内存只增不减。

六条并发铁律（每条都是真会踩的坑）

#铁律违反的后果
1每个 goroutine 都要有明确退出路径（channel 关闭或 ctx 取消）goroutine 泄漏，内存持续上涨

发生了什么：系统要把你的代码从 GitHub 拉到本地。公开仓库直接 clone 就行， 私有仓库需要凭据（不然 GitHub 不给你代码）。

小白类比

打个比方
把代码「取快递」和「拆快递」分给两个人做。

取件员（Go 进程）持有你的取件码，去柜台把包裹取出来。
拆件员（构建容器）只拿到已经取出的包裹，他根本不知道取件码是什么。

流程

为什么按 commit SHA 检出，而不是按分支名 —— 这是可复现性的关键：

按分支名检出的陷阱

webhook 说：分支 main 上有新提交 a3f9c21 ❌ 如果执行 git clone -b main ──▶ 拿到的是「此刻 main 的最新提交」 ──▶ 但在 webhook 到达和构建开始之间，可能又有人 push 了新提交 ──▶ 你构建的其实不是 a3f9c21，而是别的 commit ──▶ 界面上显示 a3f9c21，实际构建的是另一个 ──▶ 这是【欺诈】 ✅ 正确做法：精确检出 a3f9c21 git fetch --depth=1 origin a3f9c21 git checkout FETCH_HEAD ──▶ 「你看到的 SHA 就是你构建的 SHA」

--depth=1 是浅克隆：只拉最新一层，不拉整个历史。 一个大仓库的完整历史可能有几个 GB，浅克隆只要几十 MB —— 对小团队省时省盘。

GitHub 支持按任意历史 SHA 浅 fetch（已用 octocat/Hello-World 的非分支尖端提交实测）。 GitLab 侧没测到，所以设计里带了回退链：

带回退的可移植检出策略

git fetch --depth=1 origin <sha> │ 成功 ├──────────────────────────▶ git checkout FETCH_HEAD ──▶ 继续构建 │ 失败 ▼（服务器不支持按 SHA fetch） git fetch --depth=1 origin <ref> + git checkout <sha> │ 成功 ├──────────────────────────▶ 继续构建 │ 失败 ▼ 标记 failed，错误分类 = git_auth │ └──▶ 【绝不静默用分支最新代码】宁可失败，也不能悄悄构建错误的版本

exit code 的含义

退出码含义系统动作
0成功阶段 passed，继续下一阶段
非 0失败（不同数字有不同含义，但 CI 只关心「是不是 0」）阶段 failed，后续阶段全部 skipped

服务启动需要时间（加载配置、连数据库、预热缓存）。刚 up -d 完立刻探测，多半还没起来 —— 这不代表失败。重试给了它启动的窗口
为什么要求连续 3 次
防止偶然一次成功就判定健康 —— 比如服务正在崩溃循环，偶尔有一次响应了。连续 3 次才算稳定

自动回滚流程：

流程

健康检查失败 │ ▼ 从部署记录里找到【上一个成功的 deployment】 │ ▼ 用它的 image_tag 重新部署 │ ▼ 再做一次健康检查 │ ├── 成功 ──▶ 状态 rolled_back，发通知 │ └── 还失败 ──▶ 【停下】，标记需要人工介入 （不要无限回滚 —— 那会变成回滚风暴）

为什么这样设计
previous_deployment_id 显式记录「回滚到哪个」。

如果靠时间戳去猜「上一个部署是什么时候」，并发部署时时间戳可能不可靠 （两个部署几乎同时完成，谁先谁后取决于写入顺序）。

显式的关系永远比推断的关系可靠。

三条设计原则：

原则① 只允许沿边迁移，非法迁移直接拒绝

go
var allowed = map[State][]State{
    StateQueued:    {StateRunning, StateFailed},
    StateRunning:   {StateSucceeded, StateFailed},
    StateSucceeded: {StateDeploying},
    StateDeploying: {StateDeployed, StateDeployFailed},
    StateDeployFailed: {StateRolledBack, StateDeployFailed},
}

func Transition(from, to State) error {
    if !contains(allowed[from], to) {
        return fmt.Errorf("非法状态迁移 %s → %s", from, to)
    }
    return nil
}

为什么要这么严格：状态错乱是并发系统最难查的 bug

坑 / 必须守住
比如一个已经 failed 的构建，因为某个迟到的 goroutine 又把它改成 running —— 界面上就出现「失败的构建正在运行」这种鬼故事。

这类 bug 极难复现（依赖时序），极难排查。
把迁移规则写死，非法迁移直接拒绝，能从根上消灭这一整类问题。

原则② 每次迁移都写审计表

sql
CREATE TABLE build_events (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    build_id    INTEGER NOT NULL REFERENCES builds(id) ON DELETE CASCADE,
    from_state  TEXT,
    to_state    TEXT NOT NULL,
    reason      TEXT,          -- 为什么迁移（错误信息、谁触发的）
    created_at  TEXT NOT NULL DEFAULT (datetime('now'))
);

为什么这样

为什么这样设计
好处：出问题时可以回放这个构建的完整历史 —— 什么时候进队列、什么时候开始、为什么失败。

这也是论文里能画「构建时序图」的数据来源，以及答辩时演示「全流程可追溯」的证据。

原则③ 单 goroutine 串行处理同一构建的事件 —— 避免多个 goroutine 同时改一个构建的状态，从设计上消灭竞态，而不是靠加锁。

「不加锁」比「加对了锁」更好：锁会带来死锁风险、性能开销，以及「我到底有没有漏加」的长期焦虑。

第一步：日志裁剪

text
构建日志可能有几 MB，但 LLM 有上下文长度限制。
而且【塞太多反而效果差】── 这点有文献支撑：
  Roy et al. (FSE'24 Companion) 发现把事件讨论记录作为额外上下文喂给模型，
  性能【并未显著提升】──▶ 说明上下文堆砌无用，信息的【筛选】才是关键。

裁剪策略：
  取头部（前 ~50 行）  ──▶ 里面是「执行了什么命令」「什么环境」
      +
  取尾部（最后 8KB）   ──▶ 里面是真正的错误信息
      +
  中间用占位符省略     ──▶ "... [省略 12,847 行] ..."

为什么错误在尾部：程序是顺序执行的，崩溃发生在最后。
头部的价值是提供上下文（跑的是什么命令、哪个阶段）。

Analyzer 的三重价值

为什么这样设计
① 安全 —— 脱敏边界由代码定义，而不是靠 prompt 里写「请不要看密钥」。 prompt 约束是可以被绕过的（提示注入），代码约束不能。

② 准确 —— 缩小范围等于提高信噪比。

③「人为主导」落地 —— 人有具体的装置来控制 AI，而不是一句口号。 答辩时如果被问「人主导具体体现在哪」，这就是答案之一。

第四步：LOA 策略决策。LOA = Level of Automation（自动化级别）， 出自 Sheridan 的十级量表。理论依据是 Parasuraman, Sheridan & Wickens (2000) 的模型 —— 自动化不是「全有或全无」，而是四类功能各自独立地可以调自动化程度：

四类功能 × 本系统的自动化级别

功能类型在 GoPulse 里对应自动化级别理由
信息获取收集构建日志、容器退出码、diff、历史失败高人不该干这个，纯机械
信息分析日志裁剪、错误聚类、根因推断高LLM 的主场
决策选择采纳哪个修复方案、是否回滚低（LOA 4）人主导 —— AI 只提议
行动执行改代码、重跑构建、部署最低人执行 —— AI 不碰代码

这个框架的价值：把口号变成可量化的设计决策

为什么这样设计
有了它，「人为主导」不再是模糊说法，而是可以精确表述的：

「本系统在信息获取与信息分析环节采用高自动化级别（Sheridan LOA 6–7）， 在决策选择与行动执行环节刻意保留人的主导权（LOA 2–4）。」

对照：LogSage（ASE 2025）那类端到端方案在决策环节接近 LOA 7–8。
你不是做得少，是刻意在不同功能维度上选择了不同的自动化级别。

降成本

解决冷启动

为什么这样设计
它不是与人主导对立的另一个开关，而是人主导积累到一定程度后自然演化出的状态。

  「全自动模式会不会和你的『人为主导』创新点矛盾？」

全自动模式的安全边界（这条务必守住）

全自动可以做全自动永不做
重试已知瞬态失败（网络抖动、镜像拉取超时）生成并应用 AI 新写的代码补丁
应用已验证过的修复动作（知识库里有）修改 secrets、SSH 密钥、部署凭据
健康检查失败后自动回滚到前序版本删除数据、清理卷、强制覆盖
依赖小版本更新 + 全量测试通过后部署未通过健康检查就继续推进
发通知、生成日报跨越审批门槛的破坏性操作

判据：全自动只执行「确定性的、已验证的、可回滚的」动作。 凡是需要生成新内容的，一律回到 LOA 4。

配套六道护栏：① 动作白名单（AI 无法发明新动作）② 熔断降级 ③ 每日预算限制 ④ 全量审计可回放 ⑤ 默认关闭（新项目默认 LOA 4，全自动需人显式开启）⑥ 破坏性动作不可提权。

AI 无法可靠区分这两者，而这恰恰是 Zhou et al. 那 29.46% 撤销率的主要来源之一。
人在这里有不可替代的判断力。

优雅关闭为什么重要

为什么这样设计
如果你 kill 掉进程时正好有构建在跑，容器会变成孤儿 —— 没人清理，占着磁盘和内存，跑上几十次就把机器塞满了。

收到 SIGTERM 后：停止接新任务 → 等在跑的完成（给 5 分钟宽限期）→ 清理 → 退出。
这就是 sync.WaitGroup 在 Pool 里的用途。

归纳：三条贯穿全局的设计主线

主线一：宁可失败，不可静默错误

队列满       → 返回 503，不硬塞进内存
检出不到 SHA → 标记失败，绝不悄悄用分支最新代码
健康检查不过 → 回滚，绝不报告「部署成功」
慢订阅者     → 丢日志行并计数，绝不阻塞构建
诊断失败     → 不影响构建结果，绝不用假数据填充

CI 系统的信任来自于「它不会骗你」。一次「显示成功但线上是坏的」就能让用户永远不再信任它。

主线二：机器做机械的事，人做判断的事

机器做：收集日志、裁剪、脱敏、调 LLM
        匹配知识库、执行【已验证】的动作

人做：  决定采纳哪个建议
        判断「是代码错了还是测试该改」
        批准破坏性操作

而人做的判断会被沉淀成知识库
   ──▶ 让机器下次能自动做
       ↑ 这就是 LOA 动态演进

「人为主导」不是能力不足的妥协，而是基于 ICSE'26 实证数据（29.46% 撤销率）的效率最优解。

主线三：一切可追溯

pipeline_json 快照 → 当时到底跑了什么命令
build_events 审计  → 状态怎么变的、为什么
log_chunks         → 完整的原始输出
deployments 回滚链 → 上一个版本是哪个
diagnosis 证据链   → AI 为什么这么说，行号可点开验证
automation_audit   → 自动执行了什么、依据哪条规则
